# Spec：移除讲义这一类内容（`scaffold` 收敛为两条命令）

## Problem Statement（问题陈述）

仓库的内容模型是三类：笔记、讲义、作业。但「讲义」（跟课敲的示例代码）在用起来之后没有产生过独立价值：它和作业目录里的代码长得一样，却要独占第三棵树、一套独立的命名规则，以及仓库里每一处「三边对齐」的说法。

核实的现状（2026-10-25）：讲义区 10 个目录、10 个 `main.go`，其中 9 个是生成后从未填过的空骨架，唯一有内容的 `hello-world` 也只是一句 `fmt.Println`，而笔记区已有同名笔记。也就是说，这一类现在只是把每次开新知识点的成本从「做决定」抬成「做决定 + 维护一个空目录」。

同时，讲义的存在让其他约定持续付息：`scaffold` 要维护第三条命令与一张三行的种类表；术语表里 `Homework` 只能靠「与 Lecture 的区别」来定义；仓库约定、工具用法文档、设计笔记、spec 快照里共有二十余处要向它解释。

另有一处同类但尚不存在的东西：`src/projects/`。它在仓库约定与术语表里被描述成一类「将来会建」的内容，而这次收敛之后，模型里不该再出现一个不存在的种类。

## Solution（方案）

把内容模型从三类收敛为两类：**笔记（Note）+ 作业（Homework）**。

- 删掉内容区的讲义树，包括其中唯一的 `hello-world` 示例——不迁移、不归档（git 历史里取得到）。
- `scaffold` 砍掉 `lecture` 命令，收敛为 `note` / `homework` 两条；除此之外**行为逐字不变**。
- `src/projects/` 一并从模型里拿掉：仓库约定与术语表不再描述它，「将来要加一类就加一张表行」的路径写进设计笔记，而不是写进域文档。
- 域文档（仓库约定、术语表、工具用法文档、设计笔记）改成两类自洽：`Lecture` 与 `Project` 两个术语条目删除，`Homework` 改成正面定义，`Topic` / `Content` / `Scaffold` 的措辞去掉第三边。
- 已发布的 spec 快照保持冻结，作「当时发布过什么」的记录。

这次是**减法**：不新增能力、不改用法、不重构内部结构。唯一的结构性判断是继续保留表驱动的种类表——两个种类仍然一个落成文件、一个落成目录，形状差异还在，所以表仍然是唯一权威。

## User Stories（用户故事）

1. 作为学习者，我想让讲义这一整类内容被移除，这样我开新知识点时只需要在「记笔记」和「写作业」之间做决定。
2. 作为学习者，我想让内容区的讲义树连同全部内容被删除，这样内容区只剩我真的在用的两棵树。
3. 作为学习者，我想让被删掉的讲义内容可以不作归档就消失，因为它们在 git 历史里已经可取回，我不想为一个空骨架养一份档案。
4. 作为学习者，我想让笔记继续承载「跟课敲过的片段」——以围栏代码块的形式，这样我仍然能记录示例，而不需要第二个可运行目录。
5. 作为学习者，我想让作业成为仓库里唯一「可运行代码」的落点，这样「能跑的东西在哪」只有一个答案。
6. 作为学习者，我想让 `scaffold` 只提供 `note` 与 `homework` 两条命令，这样工具的命令面与我实际会做的事一致。
7. 作为学习者，当我按旧习惯敲了 `scaffold lecture ...`，我想让它像任何未知种类一样被拒绝、退出码 `2`、错误走 stderr，这样失败是显式且可预期的。
8. 作为学习者，我不想看到「`lecture` 已移除，请改用 `homework`」这类特判提示，因为那会让我以为讲义还是「一种被禁用的种类」，而它已经不存在了。
9. 作为学习者，我想让 `note` 与 `homework` 两条命令的落点、编号提示、`--dry-run`、幂等 `skip`、输出格式、退出码全部逐字不变，这样这次改动不引入任何新的使用方式。
10. 作为学习者，我想让主题编号继续是笔记与作业之间的唯一对齐手段，并继续允许缺位，这样「某个知识点只写了笔记、没写作业」不需要任何理由。
11. 作为学习者，我想让作业仍然按自己的题名走、不要求和笔记同名，这样现有的命名自由不被收敛掉。
12. 作为维护者，我想让「删掉一个种类」的改动量被实测一遍（种类表一行、模板注释、测试字面量），这样「加/减一类 = 改一行」这条设计第一次被反向验证。
13. 作为维护者，我想让 `src/projects/` 从仓库约定与术语表里一起消失，这样域文档不再描述一个模型里不存在的种类。
14. 作为维护者，我想让「把某一类加回来 = 种类表加一行」这条路径写进设计笔记，这样将来真需要时不必重推一遍设计，也不会觉得「当初没留白是个错误」。
15. 作为维护者，我想让术语表删掉讲义与项目两个条目，并把笔记 / 主题 / 脚手架 / 作业四处定义改到自洽，这样术语表里没有悬空引用（例如「与 Lecture 的区别」）。
16. 作为维护者，我想让「作业不配 `_test.go`」这条规则保留一句极短的理由，这样在拿掉 `src/projects/` 这个参照物之后，它不会变成一条没有来由的禁令。
17. 作为维护者，我想让仓库约定里留一行护栏、说明讲义是刻意移除的、不要加回，这样下一个 agent 不会因为「两类看着不对称」而顺手补回第三类。
18. 作为维护者，我想让设计笔记新增一节，记下这个问题、已定分支、已否分支与待定分支，这样「为什么只有两类」只推导一次。
19. 作为未来的我，我想让设计笔记顶部有一条状态行，说明现状以最新一轮为准、前面各段的「三类」是当时的状态，这样我读到文档开头时不会以为仓库还有讲义。
20. 作为维护者，我想让已发布的 spec 快照保持冻结、不被反向修订，这样 `docs/specs/` 仍然是「当时发布过什么」的记录，而不是被反复改写的现状说明。
21. 作为维护者，我想让所有与讲义相关的测试用例被删除或被改到作业上，并补一条「`lecture` 现在是未知种类」的断言，这样「讲义已被移除」是可执行事实而不是口头承诺。
22. 作为维护者，我想让作业骨架的断言在删掉讲义测试之后**不减少覆盖**——`package main`、有 `main()`、过 `gofmt`、目录里只有 `main.go` 这四层都要留着。
23. 作为维护者，我想让这次改动后 `go vet ./...` 与 `go build ./...` 仍然覆盖仓库全部代码，这样删掉一棵树不会悄悄缩小门禁的检查面。
24. 作为未来的我，我想让这次改动走一次完整的「分支 → 提交 → PR → 确认 → squash 合并」流程，这样单人仓的复核动作仍然被保留。
25. 作为未来的我，我想让 spec 的权威副本是 GitHub issue、仓库内留一份快照，两者内容一致，这样下一次改动有据可查。

## Implementation Decisions（实现决策）

**内容模型**

- 内容区只有两类：`Note`（笔记，Markdown 文件）与 `Homework`（作业，独立可运行目录）。`Lecture` 与 `Project` 都不在模型内。
- 讲义树整棵删除，**包括**唯一的 `hello-world` 示例。不迁移到笔记、不迁移到作业、不另建归档目录：它的内容是一句话打印，笔记区已有同名笔记承载同一个知识点，示例本身不是资产。删除前已核实该树全部已提交，历史可取回。
- `src/projects/` 不进入模型：仓库约定与术语表都不再提它。加回路径记在设计笔记里（加一类 = 种类表加一行 + 一个内容生成器），不占域文档。

**工具（`scaffold`）**

- 种类表删掉讲义一行；内容生成器与模板注释改成「作业专用」的措辞。
- **不保留「已移除」特判**：`lecture` 走与任何未知种类相同的路径——stderr 报未知种类、退出码 `2`、不写任何东西。理由：特判会让人误读成「讲义仍是一种种类，只是被禁用」，而它已经不在模型里。
- 其余行为一律不动：落点、slug 与编号校验、「下一个可用编号」提示、幂等 `skip`、`--dry-run`、每行一条结果加一行汇总、退出码 `0/1/2`、从 cwd 向上发现仓库根。
- 表驱动的种类结构保留。两个种类仍然一个落成单文件、一个落成「目录 + 入口文件」，形状差异还在，所以种类表继续是「内容区结构」的唯一权威；不因为只剩两行就内联成 `if`。
- 不引入第三方依赖、不引入配置驱动、不新增子命令、不加 `--force`/`--root`/`--with`。

**域文档**

- 术语表：删 `Lecture` 与 `Project` 两个条目；`Content` 的定义去掉讲义与项目；`Topic` 从「三边」改为笔记与作业两个维度；`Scaffold` 从「三选一」改为二选一；`Homework` 改成正面定义（自己独立完成的题目、一题一目录、题目说明记在对应笔记里），不再以「与 Lecture 的区别」存在。术语表只收活的词，死的词留在里面会让下一个 session 以为仓库还有讲义。
- 仓库约定：首句「三类内容」改为两类；目录表删掉讲义行与项目行；「三边对齐」改为笔记与作业对齐（示例改为笔记文件 ↔ 作业目录，作业按题名走、允许缺位）；命令面两条；目录与骨架仍由工具生成。
- 仓库约定的「门禁」段：拿掉 `src/projects/` 之后，「作业不配 `_test.go`」补一句极短理由——作业是一次性答案，工具是长期程序——否则它是一条没有来由的禁令。
- 仓库约定新增一行护栏：讲义这一类是刻意移除的（理由见设计笔记），不要加回。措辞与既有的「`src/` 是刻意保留的，不要拍平」同构：后者防的是重构冲动，这一条防的是「补齐对称」冲动。
- 设计笔记：新增一节，按既有的四段结构写（问题 / 已定分支 / 已否分支 / 待定分支），记录今天的核实数据、移除理由、被否掉的替代方案（迁移 `hello-world`、保留已移除的友好提示、保留 `Project` 作为未来槽位、反向修订 spec 快照、给这次改动写 ADR）。
- 设计笔记顶部新增一条状态行，指明现状以最新一轮为准、前面各段的「三类」是当时的状态。历史段落不修订。
- 已发布的 spec 快照**冻结**，不反向修订：它记录的是当时发布过什么。
- 不写 ADR：本次是移除而不是引入，加回的成本只有一张表行，三条门槛里的「难以逆转」不成立。

**交付**

- 走仓库既有的流程：分支 → 三刀提交（删内容 / 改工具 / 改文档）→ PR → 等用户确认 → squash 合并并删分支。
- 三刀提交是为了让门禁失败的定位落在最小的提交上，不是为了美观。

## Testing Decisions（测试决策）

**什么算好测试**

只断言外部可观察的结果：文件系统上出现了哪些路径、内容是什么、stdout 与 stderr 写了什么、退出码是多少。不断言私有函数的形状、不断言中间数据结构、不为日志措辞做逐字匹配（只看 `create` / `skip` / 汇总 / 「下一个可用编号」这类稳定标记）。

**seam**

- 不新增 seam。测试仍然只从**一条** seam 进入：CLI 边界上的「参数 + 工作目录 + 两个输出流 → 退出码」。参数解析、校验、规划、写入、输出与退出码全部在这条线之下。
- 不引入文件系统抽象、不 mock：在 `t.TempDir()` 里造一个带正确 module 的假仓库根，用真实文件系统断言。
- 这次改动不改变 seam 的形状，只改变穿过 seam 的用例集合。

**测什么**

- 删除讲义专属用例（创建讲义骨架、讲义区的写入失败、以讲义目录为 cwd、讲义用法错误等）。
- 讲义用例里「生成的入口文件是 `package main` 且有 `main()`」这层 **AST 断言合并进作业用例**，与作业用例已有的「逐字内容 + `gofmt` 不变 + 目录里只有 `main.go`」合并——删测试不减少覆盖。
- 其余用例里的种类字面量换成作业，语义不变（幂等、`--dry-run`、汇总、仓库根发现、参数个数、slug 与编号校验）。
- 未知种类表驱动用例补一行 `lecture`：断言退出码 `2`、stderr 带 `error:` 前缀、假仓库里除 `go.mod` 外没有多出任何东西。
- 跑完门禁三条：`gofmt -l .` 无输出、`go vet ./...`、`go build ./...` 全绿——这是「删掉一棵树之后仍然全部可编译」的端到端证据。
- 内容区不加任何测试：作业按既有约定不配 `_test.go`，这次也不会因为「要证明没坏」而破坏这条约定。

**先例**

仓库唯一的测试先例就是工具区这套外部测试包：按能力分文件（落点、校验、编号、幂等、`--dry-run`、汇总、根发现、用法），能表驱动的用表，共用同一条 CLI 入口。这次的改法是「按同一套组织方式减少用例」，不引入新的测试形态。

## Out of Scope（不在本次范围）

- 新增任何内容种类（`project` 或别的），也不预留它的种类表行。
- 改动 `scaffold` 的用法、落点、编号规则、输出格式、退出码语义，或增加 `--force` / `--root` / `--with` 一类能力。
- 重建 `src/notes/README.md` 主题索引。
- 迁移或归档讲义内容（含 `hello-world`）。
- 反向修订已发布的 spec 快照。
- 重写 git 历史（不 rebase / squash 掉讲义曾经存在的提交）。
- 引入 CI、引入第三方依赖、给作业补测试。
- 处理仓库根那个未跟踪的 `scaffold.exe` 构建产物。
