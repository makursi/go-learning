# modules-and-packages

**Go 语言的模块、包与仓库**

## 1. module、package 与 repository 的关系与区别

### 包(package) 

**包是编译的基本单位。**

官方文档:

- 同一目录下的一组 `.go` 源文件（共享同一个 `package` 声明）构成一个包。

- 包内的标识符对同包其他文件可见，跨包则通过导出（首字母大写）和导入路径访问。

- 包本身不携带版本信息，也没有独立的发布单元。

## 模块(module) 

**模块是版本化、可发布、可依赖的单位。**

官方文档:

- 一个模块是一组相关包的集合，它们一起被版本标记、一起被下载和验证。

- 模块的根目录必须有一个 `go.mod` 文件，该文件声明模块路径(module path)。

- 模块路径既是该模块所有包的导入路径前缀，也是 `go` 命令用来定位和下载该模块的关键标识。

- 模块可以包含多个包(分布在子目录中)，也可以只包含一个包。

- 模块路径通常与仓库位置对应，例如 `github.com/user/project`，对于主版本号 ≥2 的模块，路径末尾还必须带上 `/v2`、`/v3` 等主版本后缀，以满足导入兼容性规则。

## 仓库(repository) 

仓库是版本控制系统（通常是 Git）中的代码存储位置。

- 一个仓库可以包含一个或多个模块。最常见的情况是仓库根目录就是模块根目录（只有一个 `go.mod`）。也有仓库在子目录中放置多个独立模块的情况。

- `go` 命令通过模块路径推导仓库位置（通常借助 HTTP 请求中的 `go-import` meta 标签，或直接识别 GitHub 等常见托管服务），然后从仓库中按语义化版本标签或伪版本（pseudo-version）取出对应代码。

## 对应关系

仓库提供代码存储与版本标记；

模块把这些代码组织成可版本化、可依赖的单元；

包是模块内部实际被编译和导入的代码单位。你编写代码时面向的是包，管理依赖时面向的是模块，发布时则通过仓库打标签。

## 2. go.mod 与 go.sum 的作用与内容

### go.mod

**go.mod** 是模块的定义文件，位于模块根目录。它是人类可读、机器可写的文本文件，主要包含：

- `module` 指令：声明模块路径。
- `go` 指令：声明该模块所需的最低 Go 语言/工具链版本。
- `require` 指令：列出直接依赖的其他模块及其最低版本。间接依赖通常也会被记录，并带有 `// indirect` 注释。
- 可选的 `replace`、`exclude`、`retract`、`toolchain` 等指令，用于本地替换、排除特定版本、撤回有问题版本或指定推荐工具链。

`go.mod` 决定了构建时使用的依赖版本集合（通过最小版本选择算法）。

从 Go 1.16 起，构建命令默认不会自动修改 `go.mod`（使用 `-mod=readonly`），只有 `go get` 和 `go mod tidy` 等明确的依赖管理命令才会改变它。这保证了依赖变更是显式、可审查的。

### go.sum

**go.sum** 则是校验和文件，记录每个被下载模块版本（以及对应的 `go.mod`）的加密哈希。

它的作用是保证“你第一次下载到的内容，之后任何人都下载到完全相同的内容”。当 `go` 命令需要新模块时，会从校验和数据库（sumdb）获取权威哈希并写入 `go.sum`；后续下载会用本地 `go.sum` 验证内容是否被篡改。

`go.sum` 应与 `go.mod` 一起提交到版本控制，这样团队成员和 CI 都能得到一致且经过验证的依赖。

两者配合解决了“依赖漂移”和“供应链安全”问题：`go.mod` 锁定版本选择，`go.sum` 锁定内容完整性。

## 3. 依赖的增删与升级


### 添加依赖

**添加依赖**的标准流程是：先在代码中写好 import 语句，然后运行 `go get`。例如：

```
go get example.com/some/module
```

或指定版本：

```
go get example.com/some/module@v1.2.3
go get example.com/some/module@latest
```

`go get` 会解析参数（可以是包路径、模块路径或带版本查询），更新主模块的 `go.mod`（添加或调整 `require`），下载源码到模块缓存，并更新 `go.sum`。如果只是想让当前模块的导入都能被满足，也可以直接在模块根目录运行 `go get .` 或 `go mod tidy`。

**升级或降级**同样用 `go get`。先查看可用更新：

```
go list -m -u all
```

然后针对具体模块执行：

```
go get example.com/some/module@v1.3.0   # 升级到指定版本
go get -u example.com/some/module      # 升级到最新次要/补丁版本
go get -u=patch ./...                  # 只升级补丁版本
```

**删除依赖**不能简单手动删 `require` 行，因为可能还有间接依赖或测试依赖。正确做法是先移除代码中的 import，然后运行：

```
go mod tidy
```

`go mod tidy` 会根据当前源码实际使用的包，添加缺失的依赖、删除不再需要的依赖，并整理 `go.mod` 和 `go.sum`。也可以用 `go get example.com/mod@none` 主动移除某个模块的要求。

日常建议把依赖变更集中在 `go get` 和 `go mod tidy` 上，避免手工编辑导致不一致。构建命令本身默认只读，进一步减少意外修改。

### 4. 工作区模式（Workspace Mode）

当同时开发多个相互依赖的模块时（例如本地修改了一个公共库，同时在业务模块中验证），传统做法是在各个 `go.mod` 里写 `replace` 指令指向本地路径。这带来维护负担：发布前必须清理 `replace`，多模块之间容易不一致。

Go 1.18 引入的工作区模式正是为了解决这个问题。它通过一个独立的 `go.work` 文件，把多个本地模块声明为“主模块集合”，构建时统一使用这些本地版本，而无需修改任何一个模块自己的 `go.mod`。

创建工作区：

```
go work init ./mod1 ./mod2
```

这会生成类似下面的 `go.work`：

```
go 1.21

use (
    ./mod1
    ./mod2
)
```

之后可以用 `go work use ./another` 添加更多模块，用 `go work use -r` 递归扫描，用 `go work edit` 进行脚本化编辑，用 `go work sync` 把工作区解析出的依赖版本同步回各个模块的 `go.mod`。

在工作区目录及其子目录中执行 `go build`、`go test`、`go run` 等命令时，`go` 命令会把 `use` 列出的所有模块都视为主模块，优先使用本地代码。环境变量 `GOWORK` 可以显式指定或关闭工作区（设为 `off`）。工作区模式下，`-mod` 只能是 `readonly` 或 `vendor`。

工作区特别适合 monorepo 或本地多模块联调场景。发布时，开发者仍然在各自模块中用常规方式打标签和更新版本要求；`go.work` 本身通常不提交到公共仓库，或者仅作为本地开发辅助。

总结一下实际工作流：单个可发布单元用模块(`go.mod` + `go.sum`)；模块内部按目录组织包；代码存储在仓库中并通过语义化版本标签发布；日常依赖增删改用 `go get` 和 `go mod tidy`；多模块本地联调则启用工作区(`go.work`)
